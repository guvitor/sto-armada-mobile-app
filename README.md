# СТО Армада Моторс — мобильное приложение

> **Хотите установить приложение на телефон?** Инструкция — в [INSTALL.md](INSTALL.md), файл для скачивания — в [последнем выпуске](https://github.com/guvitor/sto-armada-mobile-app/releases/latest). Ниже — техническая документация для разработчиков.

Порядок разворачивания на сервере. Скрипты — разовые, запускаются через браузер или `php` с корня сайта (используют `prolog_before.php`). Дополняется по мере разработки — см. [../development_plan/tz-mobile-app.md](../development_plan/tz-mobile-app.md).

## 1. Инфоблок «Записи на сервис»

Создан вручную в админке. ID = 130.

## 2. Свойства инфоблока 130

Запустить по очереди:

1. `add_property_service_id.php` — свойство `SERVICE_ID` (привязка к элементам, `LINK_IBLOCK_ID=117` — каталог услуг).
2. `add_iblock_130_properties.php` — остальные свойства:
   - `DATETIME` — дата/время визита;
   - `STATUS` — список-справочник (`NEW`, `CONFIRMED`, `IN_PROGRESS`, `DONE`, `CANCELLED`);
   - `USER_ID` — привязка к пользователю (Фаза 2, в MVP не используется);
   - `COMMENT` — комментарий клиента.
3. `add_iblock_130_client_properties.php` — `CLIENT_NAME`/`CLIENT_PHONE` (MVP без авторизации, см. п. 6).

Все три скрипта идемпотентны — проверяют существование свойства по коду перед созданием, повторный запуск безопасен.

## 3. Доступ через REST для инфоблока 130

Вручную в админке: Контент → инфоблок «Записи на сервис» → настройки → включить «Доступ через REST». Программно не делается — риск задеть настройку неверным API-вызовом без проверки в UI.

## 4. Таблица токенов авторизации

Запустить `install_sto_auth_token_table.php` — создаёт таблицу `sto_auth_token` (хэши access/refresh токенов, сроки жизни). Идемпотентен (`CREATE TABLE IF NOT EXISTS`).

## 5. REST-метод `sto.auth.login` (Фаза 2, вне контракта MVP)

1. Скопировать `rest/StoAuthRestService.php` на сервер в `/rest/StoAuthRestService.php` от корня сайта `sto.armada-motors.com` (не `/mobile_app/rest/` — так короче путь require в `init.php`).
2. Дописать в `/local/php_interface/init.php` содержимое `rest/init_snippet.php` — подключение класса и регистрация обработчика события `OnRestServiceBuildDescription`.

Метод проверяет логин/пароль через `CUser::Login`, выдаёт `access_token` (1 час) и `refresh_token` (30 дней), хэши SHA-256 сохраняет в `sto_auth_token`. Реализован и протестирован (день 1–5), но в MVP-сценарий не входит — 19.09.2026 решено делать запись без регистрации (см. п. 6).

## 6. REST-метод `sto.booking.add`

Скопировать `rest/StoBookingRestService.php` на сервер в `/rest/StoBookingRestService.php` тем же способом, что и `StoAuthRestService.php` (см. п. 5) — регистрация обоих классов уже объединена в `rest/init_snippet.php`.

Метод принимает `name`, `phone`, `service_id`, `datetime` (`Y-m-d H:i:s`), `comment`:
- `name`/`phone` — обязательные, сохраняются в свойствах `CLIENT_NAME`/`CLIENT_PHONE` (без авторизации, MVP);
- проверяет, что `service_id` существует и активен в каталоге услуг (инфоблок 117);
- создаёт элемент в инфоблоке 130 со статусом `NEW`;
- возвращает `result` — ID созданной записи.

## 7. REST-методы `sto.booking.get` и `sto.booking.list` (Фаза 2, вне контракта MVP)

Добавлены в тот же `rest/StoBookingRestService.php` — отдельного копирования не требуется, файл уже описан в п. 6. Требуют `access_token` (система авторизации из п. 5) и привязку записи к `USER_ID` — после перехода MVP на `CLIENT_NAME`/`CLIENT_PHONE` без регистрации новые записи `USER_ID` не получают, поэтому эти методы сейчас не находят ничего своего. Рабочее состояние на день 5 (пока ещё был `USER_ID`) зафиксировано ниже для истории; актуализация — задача Фазы 2 вместе с авторизацией.

- `sto.booking.get` (`access_token`, `id`) — возвращает `status`, `status_name`, `datetime`, `service_id`, `comment` по конкретной записи. Если запись принадлежит другому пользователю — отвечает `BOOKING_NOT_FOUND`, а не «доступ запрещён»: не подтверждает даже факт существования чужой записи.
- `sto.booking.list` (`access_token`, `order` — `ASC`/`DESC`, по умолчанию `DESC` по дате визита) — список записей текущего пользователя в том же формате.

## 8. Проверка REST-доступа `catalog.product.list`

Запустить `check_catalog_rest_access.php`. Скрипт проверяет установку модулей `catalog`/`rest` и то, что метод `catalog.product.list` зарегистрирован в системе (тем же способом, каким ядро REST собирает список методов — через `OnRestServiceBuildDescription`).

Это подтверждает доступность метода на уровне модулей. Отдельно, вручную, проверить:
- у вебхука/REST-приложения для мобильного включён скоуп «Каталог» (`catalog`) — без него метод ответит `ACCESS_DENIED`;
- у нужных услуг заполнены `ID`, `NAME`, `PRICE`, `ACTIVE=Y`.

## 9. Тестирование (день 5)

Прогон через `test_rest_methods.php` (одноразовый диагностический скрипт, вызывает классы напрямую, без REST/OAuth-транспорта — см. примечание про БУС ниже). Найденные и исправленные баги:

- `StoAuthRestService::login()` — четвёртый параметр `CUser::Login()` означает не «secure», а «пароль в открытом виде» (`password_original`, по умолчанию `'Y'`); передача `'N'` ломала любую авторизацию. Убран лишний параметр.
- `StoBookingRestService::getStatusEnumId()` — `CIBlockPropertyEnum::GetList()` не поддерживает фильтр по `CODE`, нужен `PROPERTY_ID`. Переписано: сначала получаем ID свойства по коду, потом ищем enum-значение.
- Справочник STATUS изначально создавался не так, как задумано: `VALUE` содержал английские коды, `XML_ID` — случайный хеш от Битрикса. Исправлено одноразовым скриптом `fix_iblock_130_status_enum.php` (`CIBlockProperty::UpdateEnum()`, по существующим ID значений).
- `formatBooking()` — тайп-хинт `\CIBlockElement` не подходит для результата `GetNextElement()` (тот возвращает `_CIBElement`). Поправлено.
- `get()`/`list()` — в `CIBlockElement::GetList()` не хватало `IBLOCK_ID` в списке выбираемых полей (только `ID`), из-за чего `GetProperties()` у инфоблока версии 2 молча возвращал пустой массив, хотя значения свойств реально были в БД. Добавлено `IBLOCK_ID` в select.
- `formatBooking()` — поле `datetime` приходило в формате сайта (`d.m.Y H:i:s`), а не в контрактном `Y-m-d H:i:s`. Добавлена нормализация формата.

Важно для дня 6+ (Flutter): сайт работает на редакции «1С-Битрикс: Управление сайтом» (БУС), не Bitrix24 — входящих вебхуков нет. Для реальных REST-вызовов (в т.ч. `catalog.product.list`) нужно локальное приложение (`client_id`/`client_secret`) и OAuth-авторизация через браузер (`code` → `access_token`/`refresh_token`). Это отдельная задача, не решена — тестирование дня 5 обошло её, вызывая классы методов напрямую через PHP-скрипт.

После тестирования на сервере остались: диагностические скрипты (`test_rest_methods.php`, `minimal_add_test.php`, `fix_iblock_130_status_enum.php` — публично доступны по URL, без авторизации) и тестовые записи в инфоблоке 130 (созданы тестовым пользователем test1963 в ходе прогонов). Скрипты стоит удалить с сервера, тестовые записи — очистить перед реальным использованием.

## 10.5. Мини-REST для мобильного приложения (19.09.2026, обходит OAuth)

Вместо ожидания OAuth (раздел «OAuth — отложено» выше) — свой лёгкий REST в обход штатного модуля `rest`, по мотивам изученного стороннего модуля `simbirsoft.mobile` (см. `modules/simbirsoft.mobile/`): свой URL, свой статический токен в заголовке, без OAuth/`access_token`. В отличие от simbirsoft.mobile — без пользовательской авторизации, соцсетей и push (не нужны для MVP), и без хранения токенов в БД (токен один, статический, для самого приложения, не для пользователя).

Файлы — `mobile_app/mobile_api/`:
- `_cors.php` — CORS-заголовки (`Access-Control-Allow-Origin: *`, обработка preflight-`OPTIONS`). Для реального Android/iOS-приложения не нужен (CORS — браузерное ограничение), но без него эндпоинты не проверить из Flutter Web — понадобился на практике 19.09.2026.
- `_auth.php` — проверка токена приложения против константы `STO_MOBILE_APP_TOKEN`. Токен передаётся query-параметром `?token=...`, **не** HTTP-заголовком — на nginx+PHP-FPM (типовой хостинг под Bitrix) кастомные заголовки без явной настройки nginx не доходят до `$_SERVER` (проверено на сервере 19.09.2026: `X-App-Token` всегда приходил пустым). Query-параметр не зависит от конфигурации сервера — тем же способом передаёт `auth` и штатный Bitrix REST.
- `catalog.php` (GET) — список активных услуг из инфоблока 117 с ценой (первая найденная строка `Bitrix\Catalog\PriceTable` для товара — **не проверено на реальных данных**, если в каталоге несколько типов цен, нужно дофильтровать по `CATALOG_GROUP_ID`).
- `booking.php` (POST) — вызывает уже протестированный `StoBookingRestService::add()` напрямую (без Bitrix REST-модуля), тело запроса — JSON с `name`/`phone`/`service_id`/`datetime`/`comment`, токен — в query-строке того же URL.

Установка:
1. Скопировать `mobile_app/mobile_api/` на сервер в `/mobile-api/` (документ-рут).
2. Сниппет `mobile_app/rest/init_snippet.php` должен быть подключён в `/local/php_interface/init.php` (см. п. 5). В репозитории вместо токена стоит плейсхолдер `<STO_MOBILE_APP_TOKEN>`, боевое значение прописано только на сервере. Локальная копия для сборок лежит в `mobile_app/.secrets/sto_app_token`, этот файл в `.gitignore` (с 29.09.2026).
3. В Flutter-приложении передать тот же токен через `--dart-define=STO_APP_TOKEN=...` при сборке/запуске.

Пример проверки: `curl "https://sto.armada-motors.com/mobile-api/catalog.php?token=..."`.

Ответ обоих эндпоинтов — тот же конверт, что у Bitrix REST: `{"result": ...}` при успехе, `{"error": "...", "error_description": "..."}` при ошибке — чтобы не переписывать разбор ответа на Flutter-стороне.

**Статус (19.09.2026): проверено на живом сайте, оба эндпоинта работают.**
- `catalog.php` — вернул реальную услугу («Замена тормозной жидкости», 840 RUB). Пока в каталоге всего 1 услуга с ценой — не проблема кода, вопрос наполнения каталога.
- `booking.php` — по пути нашёлся и исправлен баг: не был подключён модуль `iblock` (только `rest`), из-за чего падало `Class "CIBlockElement" not found". После фикса создал тестовую запись (ID 12179283, инфоблок 130) — удалена вручную после проверки.
- Цена в `catalog.php` (первая строка `PriceTable`) подтверждена на реальных данных для текущего единственного товара с ценой — если в каталог добавят товары с несколькими типами цен, логику стоит перепроверить.

## 12. Debug APK для теста на реальном Android-устройстве (20.09.2026)

Перед первой сборкой под нативный Android нашёлся баг, не всплывавший на Flutter Web (день 8–10): в `android/app/src/main/AndroidManifest.xml` отсутствовало `<uses-permission android:name="android.permission.INTERNET"/>`. ### 14.1. Иконка приложения (временная)

### 14.2. Подпись релиза (keystore)

`android/app/build.gradle.kts` настроен на чтение `android/key.properties` (в репозитории нет — секретный файл, генерируется и хранится локально пользователем, я его не создаю и не читаю). Без файла release-сборка по-прежнему подписывается debug-ключом (не ломает `flutter run --release`), но такой APK/AAB нельзя публиковать в Play Store.

Шаблон — `android/key.properties.example`. Порядок:
1. Сгенерировать keystore (пароли вводятся интерактивно в момент выполнения команды, в проект не попадают):
   ```
   keytool -genkeypair -v -keystore android/sto_app_release.keystore -storetype JKS -keyalg RSA -keysize 2048 -validity 10000 -alias sto_app
   ```
2. Скопировать `android/key.properties.example` → `android/key.properties`, вписать пароли, заданные в п. 1.
3. **Keystore-файл и `key.properties` — хранить в надёжном месте отдельно от проекта (например, менеджер паролей + отдельная резервная копия).** Без них дальнейшие обновления приложения в Play Store станут невозможны — Google требует подписывать каждое обновление тем же ключом.

## 15. iOS: неподписанная сборка в GitHub Actions (05.10.2026)

Локально iOS не собрать: нужен macOS + Xcode 26 (требование App Store с апреля 2026), а на этой машине Windows, Xeon E5-2650 v2 без AVX2 (современная macOS в VM не пойдёт) и включённый Hyper-V. VMware не установлен (папки в Program Files пустые). Поэтому сборка — на macOS-раннере GitHub.

- Workflow: `.github/workflows/ios-unsigned.yml`. Запуск вручную (Actions → iOS unsigned build → Run workflow) или push в `main` с изменениями в `app/`.
- Шаги: Flutter 3.47.5 → `pub get` → `analyze` → `test` → `flutter build ios --release --no-codesign` → артефакт `sto_app-ios-unsigned` (неподписанный `.ipa`, хранится 7 дней).
- Токен приложения берётся из секрета репозитория `STO_APP_TOKEN` (Settings → Secrets and variables → Actions). Без секрета сборка проходит, но API в приложении не работает.
- Репозиторий публичный, поэтому минуты Actions, в том числе на macOS, бесплатны. Триггеры всё равно узкие: сборка занимает 3–6 минут, и запускать её на каждую правку README незачем.
- На устройство неподписанную сборку не поставить. Для TestFlight/App Store нужен Apple Developer Program, сертификат и provisioning profile — отдельный этап.

**Проверено: run 37283378641 (05.10.2026) зелёный за ~6 мин — analyze, test и `flutter build ios --no-codesign` прошли, артефакт ~7,6 МБ.** Собрано без секрета `STO_APP_TOKEN`. Секрет заведён 05.10.2026 из `.secrets/sto_app_token`, следующие сборки идут с токеном.

## 16. Публикация APK через GitHub Releases (05.10.2026)

Пока приложение не опубликовано в Google Play, клиенты ставят Android-версию из APK на GitHub. Репозиторий `guvitor/sto-armada-mobile-app` публичный, поэтому выпуски доступны без входа в GitHub.

- Инструкция для пользователей — `INSTALL.md` в корне репозитория: скачивание из Releases, разрешение установки из браузера, обход предупреждения Play Защиты, обновление и частые ошибки. Для iOS там указано «пока недоступно».
- Выпуск [v1.0.0](https://github.com/guvitor/sto-armada-mobile-app/releases/tag/v1.0.0) содержит файл `sto-armada-1.0.0.apk` (53,8 МБ). Это release-APK из раздела 14.5 (сборка 29.09.2026, `version: 1.0.0+1`), подписанный ключом `CN=Armada Motors` (проверено `apksigner` перед загрузкой). SHA-256 указан в описании выпуска.
- Следующие выпуски: поднять версию в `pubspec.yaml` → собрать `flutter build apk --release --dart-define=STO_APP_TOKEN=...` → проверить подпись → `gh release create vX.Y.Z <файл> --latest`. Имя файла должно быть **`sto-armada-<версия>.apk`**: на этот шаблон ссылается `INSTALL.md`. Исходный `app-release.apk` не переименовывать, а копировать.
- При переходе на Google Play: если в Play Console включено App Signing с ключом, который сгенерировал Google, версия из магазина не встанет поверх APK с GitHub. Клиенту придётся удалить приложение и заново войти в аккаунт. Чтобы этого избежать, при настройке App Signing загрузить в Play Console собственный ключ (`sto_app_release.keystore`).
